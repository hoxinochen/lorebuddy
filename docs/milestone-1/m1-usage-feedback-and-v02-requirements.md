# M1 使用反馈与 v0.2 需求依据

状态：**用户确认的产品发现记录**
记录日期：2026-08-25
边界：本文件记录使用事实与后续需求，不改变 Source、来源身份、Rights 或规则采纳状态。

## 1. 已完成的真实使用验证

M1-C4 的 20 文件 GPT Project Export 已经用于真实问答体验，而非仅完成自动
Validator。随后形成两套独立的优化语料：

| 语料 | 使用目标 | 已验证的价值 |
|---|---|---|
| GPT 特化稿 | 在 20 文件以内承载原有 GPT 使用需求 | 低文件数上传、全局任务路由和包级导航可用 |
| NotebookLM 优化稿 | 作为 Google NotebookLM 的阅读与检索语料库 | 经过重新清洗与组织，可支撑后续规则知识分析 |

两套语料均属于面向消费端的派生表达；它们不是原始 Source，也不单独证明书籍、版本、
翻译或再分发身份。

## 2. 下游工作流证据

用户已让相关流程指导或支持以下工作：

- 角色建卡；
- DND Terminal 的系统搭建；
- 测试怪物数据生成；
- 技能合规检查；
- 角色卡合规检查。

这些结果证明了“可全文阅读和检索”已有实际价值，也暴露出模型仍需在长文本中自行完成
版本选择、条件匹配、例外识别、冲突判断与来源定位。

下游测试或字段验证不等于规则的正式采纳。正式采纳仍必须保留独立的来源证据、
结构化候选、审核状态和下游接纳门禁。

## 3. 产品结论

下一阶段需要的是面向 LLM 的规则知识层，而不是另一种 Markdown 排版或单纯压缩文件数。
该层应当：

1. 按书籍、规则版本和权威上下文分组；
2. 允许用户通过 Ruleset Profile 显式选择要使用的书籍和优先级；
3. 将已审核的规则表达为可定位来源的 Rule Object；
4. 从 Rule Object 确定性编译出低推理模型可直接消费的 Rule Card / Ruleset Pack；
5. 将未知、冲突、可选规则、第三方内容和 House Rule 保持显式，不由模型静默合并。

## 4. 对 v0.2 的最小启动要求

首个实现阶段只应建立 Book Catalog、Entry-to-Book Mapping、Ruleset Profile 和
人工异常队列。它以 M1-C3 Publisher Manifest 的稳定 `entry_id`、路径和摘要为输入，
不改写 Source，不生成 Rule Object，也不进行全量语义抽取。

该阶段的主路径应当是确定性程序：所有 Entry 要么映射到一个候选书籍，要么进入明确的
review queue。模型仅在后续 Rule Object 试点中处理结构化候选和歧义，不承担批量目录归类。

## 5. 后续验收方向

v0.2 的验收以真实工作流为单位，而非只检查 Schema：

- 建卡时，模型能识别适用书籍、版本、前置条件和替代规则；
- 技能与角色卡检查时，模型能给出可追溯的合规结论与缺失条件；
- 怪物数据生成时，模型不会混合版本或遗漏动作、特性与例外；
- 在相同任务上，Rule Card / Ruleset Pack 相比原始长 Markdown 降低输入量、版本混用和条件遗漏。

具体阈值、抽样集和人工审核方式必须在 v0.2 Implementation Profile 中确认后才成为门禁。
