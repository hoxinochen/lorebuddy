# 规则书模块、规则簇与发布包边界调查

日期：2026-10-20。状态：研究结论／具体技术合同待讨论。

本文件回应用户对前轮方案证据不足的质疑。用户已认可“按事实职责维护、按用途组合”和“共享基础＋来源／专题包”的方向；本轮调查检验这些方向的适用条件，不重新把它们当成未经认可的选项，也不把认可扩大为生产授权。

本报告不修改 M2 合同、Schema、原始 Source、M1、外部交付或 Terminal；不形成正式规则批准、Package Release 或全书生产许可。研究脚本仅扫描既有文件，输出研究统计和定位证据，不生成规则候选或生产数据库。

## 1. 调查结论与证据等级

**方向值得继续，但应把“内容维护”“语义组合”“消费执行”和“安装分发”分开。首批不宜建立大量独立安装的小包，也不宜承诺整书完全可执行。**

| 判断 | 当前信度 | 支持与限制 |
|---|---|---|
| 生物本体维护专属能力，共享条目维护共享机制 | 较强 | 本地说明与反例、Open5e 子对象模型、Foundry D&D／PF2e 数据形态互相支持；不证明所有专属能力都应独立建表 |
| 保留原文，同时逐步结构化参数、条件和引用 | 较强 | 三个开源项目都保留描述，另有结构化内容；不能从“有 JSON”推导完整机器语义或 AI 正确率 |
| 内容职责与书籍导航、分发边界分开 | 较强 | 本地有无数据卡页面、跨导航入口；开源模型与内容库也不是同一划分 |
| 共享基础＋来源／专题内容是合适的组织方向 | 中等偏强 | 支持复用与来源组织并存；尚未模拟 LoreBuddy 安装、升级、冲突、撤回与权限闭合，具体物理包数未定 |
| 上轮恰好那八项职责就是最优平级模块 | 不成立／需修正 | 它混合了证据治理、内容领域、组合和视图，应当作为职责清单而不是八个平级 Package |
| 这种组织可改善全书 AI 问答与人类阅读 | 有限支持 | 既有小样本有受控评测；本轮未做全书问答、用户阅读测试或模型对照，不能给出全书收益百分比 |
| 可据此估算全书工时、自动化率或搜索延迟 | 未知 | 缺少生产吞吐、返修率和目标设备实测；不提供编造的天数、成功概率或性能保证 |

这里的信度是工程证据评价，不是统计置信区间。案例选择有目的、非随机，不能推算总体错误率。Foundry 的两个系统共用同一平台，也不算两个完全独立的架构实验。

## 4. 书籍本身提供的边界证据

[数据卡的组成部分](/Users/chenzehao/Projects/LoreBuddy/build/m1c3-obsidian-baseline/Notes/怪物图鉴2025/前言/数据卡的组成部分.md)把多项通用规则指向玩家手册，同时说明本书的怪物数据卡约定。尤其是：

1. 装备在怪物使用时可以具有已经计入数据卡的特殊效果；其他人获得该物品后使用玩家手册的物品规则。由此可直接支持“食人魔巨棒动作参数不能由玩家武器表覆盖”。
2. 施法列表可以携带限制、使用次数、施法属性及升环信息。因此引用法术需要保留调用上下文。
3. 数据卡的动作、豁免、成功仅半伤、使用限制等格式，有本书共享解释。共享机制不应全部误归为 PHB；MM 自身也提供规则约定。

## 5. 开源项目实际怎样拆分

### 5.1 Open5e：领域对象、子动作和来源分开

[Creature 模型](https://github.com/open5e/open5e-api/blob/e69ac13b49dae6a9d84abf38fc674fe1db5b392b/api_v2/models/creature.py#L213)中，CreatureAction 指向所属 Creature，CreatureActionAttack 再指向动作并保存攻击参数；动作还有顺序、使用类型、形态限制等字段。状态免疫关联 Condition，环境关联 Environment，而非给每个分类创建独立怪物库。

[Document](https://github.com/open5e/open5e-api/blob/e69ac13b49dae6a9d84abf38fc674fe1db5b392b/api_v2/models/document.py)承载出版物、发布者、系统和许可关联；[Rule／RuleSet](https://github.com/open5e/open5e-api/blob/e69ac13b49dae6a9d84abf38fc674fe1db5b392b/api_v2/models/rule.py)另外组织规则段落与顺序；[CrossReference](https://github.com/open5e/open5e-api/blob/e69ac13b49dae6a9d84abf38fc674fe1db5b392b/api_v2/models/crossreference.py)连接描述中的对象。

可借鉴：生物—能力—具体参数的层次、分类与事实职责分开、描述与结构化信息共存。不能直接沿用：其某些 key 派生方式、删除级联、全局优先级或网页交叉引用，不等同 LoreBuddy 的稳定身份、不可变来源、审核式来源映射或必需依赖合同。这里也没有证明 CreatureAction 已表达所有持续、例外和执行语义。

### 5.2 Foundry D&D：Actor 内嵌 Item，Item 内再有 Activity

[2024 狼](https://github.com/foundryvtt/dnd5e/blob/3100ca51e89fc8d7ed341d8981083556a9e4d4bf/packs/_source/actors24/beast/wolf.yml#L548)包含内嵌 Pack Tactics 和 Bite。Bite 有 attack Activity 和倒地效果，同时描述中保留体型条件；并非所有条件都成为独立全局规则对象。

[2014 狼](https://github.com/foundryvtt/dnd5e/blob/3100ca51e89fc8d7ed341d8981083556a9e4d4bf/packs/_source/monsters/beast/wolf.yml#L538)的啃咬有豁免流程，2024 狼则是体型条件下倒地。两者分别保留 rules 来源信息。这是不能按同名合并的外部实物对照，不是让外部狼替代本地来源。

[Cast Activity](https://github.com/foundryvtt/dnd5e/blob/3100ca51e89fc8d7ed341d8981083556a9e4d4bf/module/data/activity/cast-data.mjs#L23)既有法术 UUID，又有施法属性、DC／攻击修正、环阶和成分，以及可覆盖的活动信息。这直接支持“引用目标＋本地调用参数”两部分，而非每次复制一份法术后独立改写。

[system.json](https://github.com/foundryvtt/dnd5e/blob/3100ca51e89fc8d7ed341d8981083556a9e4d4bf/system.json#L252)声明 23 个 Compendium，包含生物、物品、法术、怪物特性、规则和表格，也并存旧版及新版本内容。

可借鉴：对象内能力可寻址、多活动、法术引用及局部参数、规则版本隔离。不能直接沿用：Actor 的 HP、使用次数和效果等运行字段，以及 Foundry 的宏语法、UUID 解析、缓存和引擎生命周期。

### 5.3 PF2e：内容数据与可解释的规则元素协作

[PF2e 狼](https://github.com/foundryvtt/pf2e/blob/0a67a7741c0b0e63667b06d9e11274e72aea6004/packs/pf2e/pathfinder-monster-core/wolf.json)同样有内嵌攻击与能力；Pack Attack 用开关与 DamageDice 规则元素表达，Knockdown 关联共享能力来源，并借助本地化内容显示。

[Frightened](https://github.com/foundryvtt/pf2e/blob/0a67a7741c0b0e63667b06d9e11274e72aea6004/packs/pf2e/conditions/frightened.json)在同一状态记录里保留描述、出版信息、数值与 FlatModifier；[RuleElement 基类](https://github.com/foundryvtt/pf2e/blob/0a67a7741c0b0e63667b06d9e11274e72aea6004/src/module/rules/rule-element/base.ts#L52)处理 predicate 等通用执行信息。[GrantItem](https://github.com/foundryvtt/pf2e/blob/0a67a7741c0b0e63667b06d9e11274e72aea6004/src/module/rules/rule-element/grant-item/schema.ts)还表达引用、选择预设、授予前修改和删除关系。

[system.pf2e.json](https://github.com/foundryvtt/pf2e/blob/0a67a7741c0b0e63667b06d9e11274e72aea6004/system.pf2e.json)声明 99 个 Compendium，既有按出版物／冒险组织的生物内容，也有法术、状态、装备与共享能力库。

可借鉴：共享能力与专属能力并存、谓词与局部修正、机制与执行引擎配合。不能直接沿用：将该执行语言提升为平台 Core，或认为 JSON 可脱离 PF2e 引擎直接执行。PF2e 与 D&D 同属较相近的规则家族，不能据此证明 COC 等系统的核心字段。

### 5.4 Compendium 不等于 LoreBuddy Package

Foundry [官方说明](https://foundryvtt.com/article/compendium/)明确介绍按需读取内容库、不同文档类型及系统／模块／世界来源。[模块开发说明](https://foundryvtt.com/article/module-development/)将一个模块的 Compendium 列表与包之间的 relationships 分开。

因此，23／99 是固定快照中的内部内容库数量，**不是 23／99 个可以分别下载安装、分别授权的 LoreBuddy Package**。这些项目证明了“多种内容职责可组合”，并未证明 LoreBuddy 应照着它们的目录各建一个独立发行包。

本次只参考架构和数据形态，没有将其规则内容作为本项目候选输入；代码公开与本地中文规则／图片的权利状态分别成立。

## 6. 用反例检验原模块方案

以下为原文定向阅读得到的边界结果，不是已执行的生产 Validator 测试。精确定位见 sample-probes.json。

| 样本 | 核实的现象 | 对边界的要求 |
|---|---|---|
| 食人魔巨棒 | 本地动作有独立攻击及伤害参数 | 装备关联不能覆盖已印参数 |
| 狼啃咬 | 命中后按体型倒地，无额外豁免；另有集群战术 | 共享效果不等于共享触发；整只怪物用途还需其他相关能力 |
| 眼魔 | 射线父级有选择限制；麻痹射线有重复豁免；自身反魔法引用法术 | 子能力需保留上下文，解释影响与判断可否使用的闭合范围不同 |
| 巨魔 | 再生 15，酸／火抑制下个回合再生，另有 0 HP 死亡条件 | 通用治疗规则不能吞掉专属生命周期 |
| 史拉绿蟾 | 再生 10 且要求至少 1 HP；隐形术仅自身 | 同名再生不能合并数值及条件；法术限制属于调用能力 |
| 魔法师 | 四环火球；反应在法术反制与护盾术间选择，挂同一 3／日父能力 | 不能给两法术各发一个独立 3 次池，也不能丢失反应触发来源 |
| 吸血鬼 | 魅惑引用法术但修改持续、伤害解除与结束后的认知；啃咬可产生初生吸血鬼 | 需要显式保留局部例外；生物可引用另一生物，未必是可选百科关联 |
| 水元素 | 淹没有不同 DC、擒抱容量、束缚、呼吸例外、周期伤害及他人救出 | 一个 condition 字符串不足；实际受影响列表与剩余容量是运行状态 |
| 成年红龙 | 多重攻击允许替换为指定施法；传奇资源在巢穴内不同；有充能 | 组合选择、资源池与环境条件要保持归属 |
| 拟身怪 | 同一正文行含啃咬和伪足；啃咬取决于是否被该拟身怪擒抱 | 不能按行机械切能力；状态需有施加来源关系 |
| 夺心魔 | 采脑要求目标正受擒于其触须 | 不能把任意人的擒抱都当满足前提 |
| 死亡骑士 | 光环依赖自身未失能；反应可改变本次攻击结果；赎罪影响复活 | 需要上下文输入及非战斗条件，不能一律假定可自动判定 |

这组反例没有迫使我们推翻“专属能力归对象、共享机制单独维护”，但迫使我们补充：父子上下文、共享资源、调用修正、来源特定的关系和外部状态。

### 6.1 数据类型与维护归属不能一一对应

[变形术](/Users/chenzehao/Projects/LoreBuddy/build/m1c3-obsidian-baseline/Notes/玩家手册2024/第七章：法术/法术详述/四环.md:442)引用满足条件的野兽数据；生物的施法又引用法术。若将整个“生物模块”和整个“法术模块”机械转成互相依赖的大包，容易形成包级环。

[野兽召唤术](/Users/chenzehao/Projects/LoreBuddy/build/m1c3-obsidian-baseline/Notes/玩家手册2024/第七章：法术/法术详述/二环.md:718)直接定义野兽灵魄，其 AC、HP、攻击与形态依赖施法环阶、施法者数据和环境选择。

建议：灵魄可以复用生物数据类型，但定义维护归属随该法术内容；不因“看起来是一张生物卡”就强制放进 MM 怪物包。变形术的野兽选择应表达适用集合和实际已安装覆盖，而非要求拥有所有野兽内容才能阅读法术。

由此修正上轮线性依赖示意：内容关系可以双向，某项用途的必需集合和安装包依赖须另外设计；查询时的按需展开也不等于安装 Manifest 可以临时不锁版本。

## 7. 调查后的模块与封包建议

### 7.1 四类职责

1. **证据与治理**：复用既有 Source、Catalog、Mapping、Review、Rights 与 Profile；保存输入身份、精确范围和裁决。不新建第二套来源权威。
2. **内容维护**：共享规则、生物／能力、法术、装备物品、角色构筑、世界／冒险内容。各有明确维护对象；跨领域结构可以复用，但身份与来源不因此合并。
3. **语义组合**：规则簇围绕具体用途组织条款、前提、限制、例外和关系；新关系和解释需要依据及审核，不在组合层独立复制并改写原能力参数。
4. **消费与分发**：从固定内容生成阅读卡、AI 输入、索引摘要和消费者候选；包定义安装、版本、权限和兼容边界。运行中的骰果、HP、资源与状态实例留给消费者。

这四类是职责分层，不是四个部署服务，也不要求新增四套物理数据库。当前 M2 的最小 Clause、来源绑定、候选／批准边界可复用；D&D 的攻击、资源、调用修正和生物类型属于待确认扩展，不能暗塞进现有封闭核心字段。

### 7.2 首批封包的修订建议

维持已认可的共享基础＋来源／专题方向，但第一版先评估一个安装集合，内部有明确版本的基础与 MM 样本内容组件。物理上是否多个归档、哪些组件成为独立 Package，以依赖、授权与更新实验确定。

- 不按怪物类型、CR、栖息地各自发行；先用作筛选与导航。
- 不为每次抽到的共享条款新建一个独立安装包。
- 不把所有机制塞进一个永远增长的基础包；先定义有限用途的覆盖。
- 需要法术／生物互相引用时，先按具体对象集合和用途判断，而非两套全库必需互装。
- 面向用户可以提供“安装怪物图鉴及其所需规则”的一次操作；内部仍分别维护身份、版本与授权。

整书一个安装入口仍然可以有良好体验；问题在于不要让“一个下载入口”强迫所有内容只能同版修订、同权利发布或同表维护。

### 7.3 引用至少应分别说明

| 维度 | 讨论建议 |
|---|---|
| 目标 | 稳定对象／能力身份、具体修订、语言和适用规则上下文；不靠显示名解析 |
| 用途 | 解释引用、规则使用／调用、组成关系、分类或延伸阅读等；不能全是一个无类型 related_to |
| 本地上下文 | 父能力约束、参数、局部例外、共享资源归属，及逐项来源 |
| 必需性 | 对声明用途必需、按具体分支必需、可选关联、外部运行输入 |
| 完成度 | 原文覆盖、参数抽取、关系审核和消费者执行支持分别说明 |
| 缺失行为 | 能读到什么、不能判断什么、阻断哪些正式出口；不得静默用同名对象补齐 |

这是语义清单，尚不指定新字段名、Schema 或状态枚举。精确修订、可兼容范围、Profile 选择与撤回策略仍需合同设计。

## 8. 能给出的方向预估与不能给出的工期

**可以较有依据地预估：**

- 先交付可靠读取、检索和显示，再按能力补足规则关系，比一次性承诺全自动执行更符合目前输入现实；但每个出口必须声明完成度。
